01 — Product read

What this actually is

The brief lists features. Features are not a product. Before choosing a database column, it is worth being precise about who sits in front of this and what a good five minutes looks like for them.

The user is a child between five and ten. That span is enormous. A five-year-old is pre-literate, counts on fingers, and loses interest in about four minutes. A ten-year-old reads fluently, does long division, and will notice — and resent — being patronised. Treating them as one audience produces something that fails both.

So the product resolves to a single repeated unit: a ten-question session, in one topic, at the child's current level for that topic. Everything else in the brief hangs off that unit. Score is a property of a session. Progress is the series of sessions. Badges are predicates over that series. The parent dashboard is a read model of it. Get the session right and the rest is reporting.

Decision 01

Level lives on the topic

Not one level per child. A child can be fluent in addition and lost in division; a single number mis-serves both. The level is a property of (child, topic).

Decision 02

Five levels, three names

The brief asks for at least three difficulty levels. The child sees three — Easy, Medium, Hard. The engine runs five, so adaptation has somewhere to move without visibly demoting anyone.

Decision 03

Attempts are an event log

Every answer is appended, never updated. XP, streaks, charts and badges are all derived from that log. Nothing needs backfilling when the scoring rules change.

Who signs in

The brief asks for basic authentication. The naive reading — give the child a username and password — is wrong for a five-year-old who cannot yet spell their own surname. The security boundary is the parent account: email and password, argon2id, JWT. Child profiles live under that account, and choosing one is a tap on a picture, which mints a short-lived child-scoped token. Every child-data endpoint checks that token's subject against the row it is about to touch, so one parent's session can never read another child's attempts.

02 — Process models

The three processes

Three BPMN 2.0 models, hand-authored as XML with diagram interchange, sitting in docs/bpmn/. They are not pictures of BPMN — drop any of them on demo.bpmn.io or open them in Camunda Modeler and they load as editable models.

2.1  Onboarding

The short one. Its only interesting feature is that both failure paths are modelled: a bad password loops back without telling the attacker whether the account exists, and an out-of-range age is caught by a boundary error event rather than being silently clamped.

2.2  The practice session

This is the product. Four lanes, twenty-six nodes, and three decisions you can read straight off the shape of it.

The correct answer goes down, not out. Follow Generate exercise and the next hop is into PostgreSQL, not into the browser. The DTO that reaches React carries the operands and the four choices; the answer stays in the row. Validate ownership then re-reads it server-side. A child of six will not open devtools, but a reviewer will, and grading on the client is the kind of shortcut that costs an offer.

A wrong answer forks. The parallel gateway is the most important symbol in this diagram. One branch returns immediately with a static hint; the other calls the language model in the background and swaps its explanation in when it arrives. Put the model on the critical path instead and every wrong answer becomes a three-second freeze for a child whose attention you have already lost.

The idle timer is non-interrupting — the dashed boundary circle. After forty-five seconds the choices wiggle. The turn does not end, nothing is deducted, and no clock is ever shown. Response time is still recorded, because adaptation needs it, but it is never used against the child.

2.3  The AI tutor

The brief says that if AI is used, its responses must be checked. This model is that requirement drawn out in full. Note what it does not contain: a path where a model failure reaches the child. Every branch converges on Deliver hint, and four of the five ways through end at the static template.

03 — Architecture

Four boxes and one that is deliberately outside

Two deployable services, one database, and a model daemon that is not part of the deployable unit. That last point is the only genuinely interesting thing about this topology, and it is worth being explicit about why.

Why Ollama is outside the Compose network

The obvious move is to add an ollama/ollama service to compose.yaml and call it done. It is the wrong move here. Model weights are gigabytes — the recommended phi4:14b is 9.1 GB — and baking them into an image or pulling them on first boot turns docker compose up from a thirty-second operation into a long download on a machine that may not have the disk for it. Worse, it makes the reviewer's first experience of the project a progress bar.

So the API reaches the host daemon over host.docker.internal, and treats it as an optional dependency. TUTOR_ENABLED=false yields a complete, fully working product with static hints. That is not a compromise smuggled in — it is the same fallback path the tutor model already routes to on timeout, exercised by default.

On Linux hosts

host.docker.internal does not resolve by default. The API service needs extra_hosts: ["host.docker.internal:host-gateway"] in compose.yaml, and Ollama must be bound to 0.0.0.0 via OLLAMA_HOST rather than loopback. Both belong in the README, because a reviewer on Linux hitting a silent connection refusal will read it as a broken project.

Module boundaries in the API

NestJS modules map one-to-one onto the nouns in the process models, which is the point of having drawn them first:

src/
  modules/
    auth/        // argon2id, JWT pair, child-scoped tokens, guards
    children/    // profiles, per-topic levels
    exercises/   // the generator — pure, deterministic under a seed
    sessions/    // open, serve next, finish, summarise
    attempts/    // submit, grade, append to the log
    progress/    // XP, streaks, badges, chart series — all derived
    tutor/       // ollama client, safety gate, cache, fallback
  common/
    filters/     // one exception filter, one error envelope
    pipes/       // DTO validation
prisma/
  schema.prisma
  seed.ts        // demo parent + two children with real history

The exercise generator is deliberately a pure function of (topic, level, seed). That makes it unit-testable without a database, and it means a failing case from a real session can be reproduced exactly from the seed stored on the exercise row.

Nine tables

The one that matters in an interview

If a reviewer asks a single database question, it will be about exercises.correct_answer. The answer: the exercise is generated and persisted server-side before the question is rendered, the response DTO omits the column, and POST /attempts grades by re-reading the row. The client is never told the answer and is never trusted to grade. Everything else in this schema is ordinary; this is the part with a decision in it.

Derived, not stored

Accuracy, current streak, XP by day, per-topic mastery and the parent dashboard's charts are all queries over attempts. Only children.xp_total and child_topic_levels.level are cached, because they are read on every single request in the session loop. Both can be rebuilt from the log, and a recompute command that does so is worth the forty minutes — it turns a scoring bug from a data migration into a rerun.

The response to a wrong answer

This is the shape that makes the fork in the process model real. POST /attempts returns in single-digit milliseconds and never waits for the model:

{
  "correct": false,
  "correctAnswer": 12,          // safe now — the attempt is recorded
  "xpEarned": 0,
  "hint": {
    "text": "Try counting up from 7 on your fingers.",
    "source": "static",     // shown immediately
    "ticket": "h_9f2c…"      // null when TUTOR_ENABLED=false
  },
  "progress": { "answered": 4, "of": 10, "correct": 3 }
}

The client shows hint.text at once. If ticket is present it polls /hints/:id twice at 1.5 s and then gives up, keeping the static hint. No websockets, no queue, no extra infrastructure for what is a two-request interaction.

Error envelope

One exception filter, one shape, and one field that most APIs do not have:

{
  "error": {
    "code": "EXERCISE_ALREADY_ANSWERED",
    "message": "Attempt rejected: exercise 84 already has an attempt.",
    "kidMessage": "You already answered that one! Here comes the next."
  }
}

message is for the developer and the logs. kidMessage is what the interface is allowed to render. Without that split, either the child sees a stack-trace-flavoured string or the logs lose the detail — and a child hitting a 500 is a product failure whatever the cause was.

06 — The local tutor

Trusting nothing the model says

Running locally removes the key-leak problem the brief warns about — there is no key. It does not remove the harder problem, which is that a 14-billion-parameter model will, given enough attempts, confidently tell a seven-year-old that 8 − 3 is 6.

Choosing the model

Fourteen models are pulled on this machine. Five are :cloud tagged — gpt-oss:120b-cloud, kimi-k3:cloud and friends — which route to ollama.com. Using one of those would quietly reintroduce an external dependency and an account, and destroy the "no key, no egress" claim. They are excluded on principle, not on capability.

ModelSizeVerdict
qwen2.5-coder:7b4.7 GBDefault, on measurement. Median 11.7 s per hint on the build machine. Code-tuned, so the prose is stiffer, but it obeys the schema and it finishes.
phi4:14b9.1 GBBetter mathematical prose, and the intended default until it was timed: 22.7 s per hint with no GPU offload. Worth it only on a GPU, where both drop to 1–3 s.
qwen3.6:35b-a3b22 GBMixture-of-experts, ~3 B active, so quicker than the size suggests — but it emits reasoning that must be stripped. Needs think: false.
mistral-small:22b12 GBWarmest natural language of the set. Noticeably slower. A reasonable swap if hint quality disappoints.
nexus1:1b1.3 GBToo small to hold the constraint reliably. Useful only as a latency floor in testing.

Shape is constrained, meaning is checked

Ollama supports passing a JSON Schema as format, which constrains decoding — the model cannot emit a response that violates the shape. That removes parse failures as a class, and lets the verification layer spend its effort on semantics instead of brackets:

{
  "type": "object",
  "properties": {
    "hint":      { "type": "string", "maxLength": 180 },
    "strategy":  { "type": "string", "enum":
                   ["count_on", "number_line", "break_apart",
                    "repeated_addition", "inverse", "group_share"] },
    "encouragement": { "type": "string", "maxLength": 60 }
  },
  "required": ["hint", "strategy", "encouragement"]
}

The seven checks

  1. Strip reasoning. Remove any <think> block before anything else looks at the text. Reasoning models leak it; qwen3.6 certainly does.
  2. Re-validate the schema with Zod anyway. Constrained decoding is the daemon's promise, not the API's guarantee.
  3. Answer-leak. The correct answer must not appear as a standalone number in hint. A hint that gives away the answer is not a hint.
  4. Numeric sanity. Every number in the hint must be one of a, b, or a counting number ≤ 12. This is the check that catches the real failure mode — a small model inventing arithmetic mid-explanation.
  5. Length. Two sentences, 180 characters. Enforced, not requested.
  6. Vocabulary. Word length and a banned-list check against an age band. "Subtrahend" fails for a six-year-old.
  7. Shape of the text. No URLs, no markdown, no code fences, no second language.

Any failure discards the output, logs it raw for inspection, and returns the static template. The failure rate is a number worth putting in the README — it is evidence the verification is real rather than decorative.

Cold start is the bug you will hit first

Ollama unloads a model after five minutes idle. The next request then pays the full load — twenty seconds or more for 9 GB. During a demo that reads as a hang. keep_alive: "30m" plus a warm-up call on API boot turns it into a one-time cost at startup, where nobody is watching.

Five levels, and a rule that will not thrash

The child sees three tiers because the brief asks for three and because a child who is told they have been moved from level 4 to level 3 has been told they are worse than they were yesterday. The engine keeps five so it can adjust without that ever being visible.

Adaptation is the default, not the only route

Difficulty that only moves by itself is difficulty nobody can find. A child picks Easy, Medium or Hard on the topic tile before a round; a parent sets the exact level per topic in the dashboard. The adaptive rule then carries on from wherever it was set, so either choice steers rather than pins — and a tier choice is persisted rather than applied for one round, because a setting that silently reverted would have been decoration.

Choosing a tier you are already in is a no-op. A child at level 2 who taps “Easy” stays at 2 rather than being pushed back to 1 for agreeing with where they already are.

// evaluated after every attempt, per (child, topic)
const window = lastAttempts(childId, topic, 5);
const accuracy = window.filter(a => a.isCorrect).length / window.length;

if (window.length < 5 || attemptsAtLevel < 5) return level;   // not enough signal
if (accuracy >= 0.8) return min(level + 1, 5);
if (accuracy <= 0.4) return max(level - 1, 1);
return level;

The attemptsAtLevel < 5 guard is what stops oscillation. Without it, a child at the boundary bounces between two levels every other question, and the questions stop feeling coherent. Response time is recorded and available to the rule, but is deliberately not used for promotion — a child who reads slowly is not a child who has failed to learn subtraction.

Distractors are pedagogy, not noise

Three wrong choices per question, and they are chosen, not randomised. For 7 + 5 the distractors are 11 (off by one, a counting slip), 2 (the subtraction result — wrong operation), and 13 (off by one the other way). Each wrong answer therefore identifies a specific misconception, which is what makes the tutor hint targetable: the model is told which distractor was chosen, and can address that error rather than re-explaining addition from scratch. A random number between 1 and 20 would be eliminated on sight and teach nobody anything.

Typing, not only picking

The brief allows multiple choice or typed input. Both are on screen at once, on every question, at every level: four options to tap and a keypad beneath them to type. Four options alone let a child score 25% by guessing and eliminate their way to the rest.

On roughly 30% of Medium and Hard questions none of the four options is correct, and the child has to work the answer out and type it. Levels 1–2 never do this — noticing that no option fits means holding two ideas at once, working out the answer and then spotting its absence, which is too much at five.

Because the keypad is permanently on screen this rewards checking rather than punishing guessing: the honest route is always available, so a child who works the answer out first is never caught out. That would not hold if typing were hidden behind a button.

Why this is not a UI change

The exercise row stores answerInChoices. A tapped answer must be one of the four; a typed one may be any number, because on a trap question the correct answer is deliberately absent — so POST /attempts has to decide which rule applies from the stored row rather than from what the client claims.

And that flag is never serialised to the browser. Knowing it client-side would give away that the options can be ignored, which is the whole point of the question. It comes back only in the attempt result, once the answer is recorded and can no longer be changed — where the interface uses it to say “none of the buttons was right that time” rather than leaving a child puzzled about why every option failed.

The distractors are still chosen pedagogically in both cases, because those values are what let the tutor name the misconception behind a wrong answer.

08 — UX for small humans

Nine rules, each with a reason

  1. No visible timer, ever. Response time is recorded for adaptivity and never shown. A countdown converts a game into a test, and five-year-olds fail tests by freezing.
  2. Near-zero reading load below age seven. The question is 7 + 5 = ? in very large glyphs. The instruction is an icon and optional audio, never a sentence. A child who cannot read the interface cannot use the product, however good the math engine is.
  3. Four choices, 64 px minimum targets, widely spaced. Small hands mis-tap, and a mis-tap recorded as a wrong answer corrupts the adaptivity data as well as the child's mood.
  4. Wrong is quiet. The chosen tile settles back, the correct one lights up, the hint appears underneath. No red flash, no X, no buzzer. The product's job at that moment is to keep the child in the session.
  5. Distractors that mean something — see the previous section. This is a UX decision as much as a pedagogical one.
  6. Progress is ten dots, not a percentage. Under-eights do not read percentages. They can see four dots filled and six empty.
  7. Every session ends on something that improved. The summary is built to find a true positive — a faster answer, a first correct division, a longer streak — because a screen that only reports 3/10 teaches a child that they are bad at math.
  8. One decision per screen. Pick a child. Pick a topic. Answer. Never two at once.
  9. Read the question aloud via the Web Speech API. Browser-native, no backend cost, no model call — and it satisfies the voice-based questions bonus for roughly an hour of work while genuinely serving the youngest users.
The test to apply

Sit a real five-year-old in front of it without explaining anything. Every place an adult has to intervene is a bug, and the brief grades exactly this — bolalar uchun UX'ni mustaqil o'ylash. Rules 2, 4 and 6 above all come from watching this go wrong in practice.

Where the AI-assistance answer comes from

The brief asks the candidate to explain where they used AI and to understand the generated code. The defensible version of that answer is structural, not apologetic: the process models above were the thinking, and they were done first. Generated code that implements a model you drew is code you can walk a reviewer through. Generated code that is the design is not.
